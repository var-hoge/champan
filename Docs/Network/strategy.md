# ネットワーク同期の作戦

champan のネットワーク対戦を成立させるための方針をまとめる。
[design.md](design.md) が「何を作るか」、この文書が「どう作るか」を扱う。

実装中に何度も同じ種類の失敗を繰り返したため、その原因と対策も記録する。

## 0. 前提

| 項目 | 内容 |
|---|---|
| SDK | Photon Fusion 2 / Shared Mode |
| 対戦形態 | 最大 4 人。1 台に複数人が座る構成を許容する |
| シーン | ローカル対戦とネットワーク対戦で共通のものを使う |
| 決定権 | MasterClient (ホスト) を唯一の真実とする |

**ゲームロジックは書き換えない**のが原則。champan の移動・当たり判定は自作で、
決定的 (どの台でも同じ計算結果になる) ではない。
決定性を前提とする方式 (入力だけを送る完全同期) は採らない。理由は 8 章。

## 1. 権威モデル

「誰が決めるか」を対象ごとに固定する。ここが曖昧だと、
台ごとに違う結論が出て破綻する。

| 対象 | 権威 | 理由 |
|---|---|---|
| プレイヤーキャラ | そのキャラを操作する台 | 操作の応答性を最優先する |
| バブル、リスポーンバブル | ホスト | 配置と数が全員で一致する必要がある |
| 王冠、シールド | ホスト | 勝敗判定の根拠になる |
| 試合の進行、勝ち点 | ホスト | 勝敗の唯一の真実 |
| 画面遷移 | ホスト | 全員が同じ画面にいる必要がある |
| CPU | ホスト | 判断を 1 箇所に集約する |
| エフェクト、SE、カメラ | 各台 | 見た目だけ。ずれても成立する |

### 権威の要求は「権威に依存しない場所」から行う

**Fusion の Shared Mode では、権威を持たないオブジェクトで `FixedUpdateNetwork` が呼ばれない。**
そのため「各オブジェクトが自分で権威を取りに行く」実装は成立しない (堂々巡りになる)。

権威の要求は `NetworkGameLauncher` (通常の MonoBehaviour) から行う。

また、他の台が持つ権威を奪うには、プレハブの `NetworkObject` に
**`AllowStateAuthorityOverride`** が必要。これが無いと要求は黙って無視される。

## 2. キャラの移動同期

### NetworkTransform は使わない

`NetworkTransform` は自身が座標を管理する前提で、**描画時に自分の持つ値で `transform` を上書きする**。
champan の `MoveCtrl` は `Update` (ProcSystem) で `transform.position` を直接動かすため、
その移動が毎フレーム打ち消される。

そのため座標は自前で配る。

- **権威側**: `FixedUpdateNetwork` で `SyncPosition` に現在座標を書く
- **非権威側**: `Render` で `SyncPosition` へ補間して追従する
  (`Render` は権威の有無に関わらず呼ばれる)

補間はフレームレートに依存しない形で行い、大きく離れたときは補間せず即座に合わせる
(リスポーンやワープのため)。

### 向きは別途配る

向きは速度から決まるが、非権威側では `MoveCtrl` を止めているため速度が変化せず、
向きも変わらない。`NetworkTransform` の対象は根の `transform` であり、
向きを表すメッシュ (子) の回転は含まれない。

そのため向きは真偽値として別に配る。

### 非権威側で止めるもの / 止めないもの

| 対象 | 扱い | 理由 |
|---|---|---|
| `MoveCtrl` | 止める | 自前で座標を動かすと配られた座標と二重になる |
| `TadaRigidbody2D` | 止める | 同上 |
| ローカルの入力 (`PlayerInputReader` / `CpuInput`) | 止める | 手元の操作で他人のキャラが動いてしまう |
| **コライダー** | **止めない** | 止めると他のキャラが乗れなくなる (3 章) |

## 3. ギミックの同期

### 生成と破棄

- **生成**: ホストだけが行う。配置や数が乱数で決まるため、各台で生成すると必ず食い違う
- **破棄**: ホストだけが行う。非権威側が勝手に破棄すると同期が壊れる
- **判定処理** (バブルの破裂など): ホストだけが実行する。
  非権威側でも走らせると、破棄されないまま見た目だけ変化する「見えないオブジェクト」が残る

### 位置

キャラと同じ方式で配る。`NetworkTransform` は使わない。

### 物理を止めるときはコライダーを残す

**`Rigidbody2D.simulated = false` はコライダーごと物理世界から外す。**
これを非権威側のバブルに使うと、その台では**バブルに当たり判定が無くなり**、
自分のキャラが乗れず、落下し続ける。

物理を止めたい場合は `bodyType` を `Kinematic` にして、`simulated` は `true` のまま保つ。
配られた座標で位置を決めつつ、当たり判定は残る。

### 生成のタイミング

Fusion がシーンをロードしている最中は生成できない
(プレハブの読み込みが完了扱いにならず例外になる)。
`NetworkSession.IsReadyToSpawn` が true になってから生成する。

## 4. シーケンスの同期

### 遷移はホストが決め、全員が Fusion のシーンロードで追従する

シーン上の `NetworkObject` を全員で共有するには、Fusion のシーンロードを通す必要がある。
`TransitionManager` が独自にシーンを読み書きすると Fusion が把握できず、
後から参加した台でシーン上のオブジェクトがネットワーク対象にならない。

分岐は `TransitionManager` の内部に入れる。呼び出し側 (各 UI Manager) は変更しない。

### 状態は「変化時に送る」のではなく「現在値を配り続ける」

変化した瞬間にだけ送ると、**それ以前に合流した台へ何も伝わらない**。
実際、ホストがボタンを押した後に参加したゲストへ進行状況が伝わらない不具合が起きた。

`[Networked]` な現在値を持たせ、毎フレーム反映する。

### 画面ごとの扱い

| 画面 | 方針 |
|---|---|
| タイトル | ホストが操作。選択項目・決定・演出開始をゲストへ配る |
| キャラセレクト | 各台が自分の席だけ操作。席ごとの状態 (参加、カーソル位置、決定、座標、向き) を配る |
| ルール選択 | ホストのみ操作可。選択肢の番号を配り、ゲストは同じ経路で反映する |
| 対戦 | 権威モデル (1 章) に従う。フェーズ・勝ち点・勝者・ラウンド終了を配る |
| リザルト | 勝者を配り、次の遷移はホストが決める |

### 演出は「同じ経路を通す」

受け取り側でも、ローカル操作時と同じ関数を呼ぶ。
状態だけ反映して見た目を別に書くと、必ず食い違う。
カーソル移動もアニメーション付きの移動処理を再生する。

## 5. 席と入力

### 3 つの番号を区別する

| 番号 | 意味 | 誰が決めるか |
|---|---|---|
| `PlayerRef` | ネットワーク上の台の識別子 | Fusion |
| 席番号 (`playerIdx`) | ゲーム内の 1P〜4P | ホスト (席テーブル) |
| ローカル番号 | その台の何番目のコントローラか | 各台 |

**1 台に複数人が座るため、この 3 つは 1 対 1 に対応しない。**
「2 台目の席 2」は「その台のローカル 1 人目」が操作する。

変換は `SeatInput` に集約する。各所で個別に変換すると必ず食い違う。

### CPU の扱い

- 人間が着いていない席が CPU 席になる。
  席テーブルは全員に複製されているため、どのピアでも同じ結論になる
- CPU はホストが動かし、その結果が配られる
- CPU を出すかどうかは既存のルール設定 (`IsExistCpu`) に従う

**未対応**: キャラセレクトで参加しなかった枠を CPU にする。
現在は対戦シーンに入ってから CPU 席を確定しているため、
キャラセレクトの時点では空席のままになる。
席テーブルとキャラセレクトの状態を突き合わせ、
「参加していない席 = CPU」として扱う必要がある。

## 6. 切断・クラッシュへの対策

現時点で**未実装**。展示で使うなら必須の項目。

### 想定する事象と方針

| 事象 | 方針 |
|---|---|
| ゲストが落ちた | その席を CPU に切り替えて試合を継続する。席テーブルから解放する |
| ホストが落ちた | Fusion が別のピアを MasterClient に昇格させる。昇格した台が権威を引き継ぐ |
| 一時的な回線断 | 数秒は待つ。復帰したら同じ席に戻す |
| 完全な切断 | タイトルへ戻す。試合中なら中断を全員に知らせる |

### 実装で必要になること

1. **切断の検知** — `INetworkRunnerCallbacks.OnPlayerLeft` を受け、席テーブルから解放する
2. **席の解放と CPU 化** — `NetworkSeatTable.ReleaseSeats` は用意済み。呼び出しが未接続
3. **ホスト移譲への追従** — 権威を持つオブジェクト (バブル、王冠、試合状態) を
   新しいホストが引き継ぐ。`StateAuthorityChanged` を受けて再初期化する
4. **`DestroyWhenStateAuthorityLeaves` の見直し** — Player プレハブにこのフラグが付いている。
   権威を持つ台が抜けるとキャラが消えるため、席を CPU に切り替える方針と矛盾する
5. **再接続** — 同じ `PlayerRef` で戻れるとは限らない。
   席の復帰には別の識別子 (端末ごとの ID) が要る
6. **中断表示** — 「接続が切れました」の表示と、タイトルへ戻る導線

**優先度**: ゲストの切断 → ホストの切断 → 再接続。
展示では「落ちたら試合が止まって全員が困る」のが最悪なので、
まず「落ちても試合が続く」ことを担保する。

## 7. 実装の原則 (今回の失敗から)

同じ種類の失敗を繰り返したため、原則として明文化する。

### 初期化は順序に依存させない

`Start` と `Spawned` の前後、席テーブルの到着、CPU 判定の確定は、
すべてタイミングが変わりうる。**一度だけ読んで保持する実装は必ず壊れる。**

- 参照は遅延解決にし、決まるまで毎フレーム試す
- 一度読んだ値をキャッシュせず、必要なら毎フレーム反映する
- 待機には必ずタイムアウトと、失敗が分かるログを付ける

### 待つ対象は「本当に必要な条件」にする

「席の準備完了」を待っていたが、生成に本当に必要だったのは
「シーンのロード完了」だった。**条件を代理で表さない。**

### 判定に `GetActiveScene()` を使わない

Fusion はシーンを加算ロードしてから後でアクティブにする。
シーンを判定したいときは、読み込まれたシーン名を直接受け取る。

### 例外は処理ごと止める

`Start` の中で例外が出ると、その後の処理が丸ごと飛ぶ。
バブルが 1 つも生成されなかった不具合はこれが原因だった。
非同期処理 (`UniTask.Forget`) の例外は握り潰されるため、必ず try/catch でログを出す。

### 破棄のタイミングが違う

`Runner.Despawn` は即座に、Unity の `Destroy` はフレーム末に破棄する。
毎フレーム構築するリストを回す ProcSystem では、前者で死んだ参照に触れる。

### シーン切り替えで止まらないものがある

`UniTask` のループはシーンが変わっても止まらない。
破棄済みのオブジェクトに触れて例外になるため、抜ける条件を入れる。

## 8. 採らない方針とその理由

### 入力だけを送る完全同期 (ロックステップ)

スマブラのような方式。通信量が少なく、同期ずれが原理的に起きない利点がある。

**採らない理由**: 全台で計算結果が完全に一致すること (決定性) が前提になる。
champan には決定性を壊す要素が多数ある。

- `Random.Range` (バブルの数・位置・大きさ、シールド値、SE 選択)
- フレームレートに依存する `deltaTime`
- 浮動小数の演算順序に依存する自作物理
- 演出 (DOTween) がゲームロジックに絡んでいる

対応するにはゲームロジックの作り直しになる。
また Fusion に完全同期モードは無く、Photon では Quantum という別製品になる。

### Fusion の Host Mode (予測とロールバック)

見た目の応答性は最良だが、`FixedUpdateNetwork` と `[Networked]` 状態が前提で、
移動・ステート・当たり判定を全面的に書き換える必要がある。

## 9. 検証の方法

### Multiplayer Play Mode の制約

- 仮想プレイヤーは AssetDatabase が読み取り専用。
  Fusion の設定アセットの成果物が古いと読み込みに失敗する
- ログはメインエディタの Console に出ない。
  `Library/VP/<id>/Logs/Editor.log` を直接読む

**入力とフレームレートは正常に動く** (実測済み)。
問題が起きたとき、まず環境を疑うのは誤り。**測定してから判断する。**

### ログの設計

原因究明のためのログは、**次の 1 回で原因が確定する**ように仕込む。

- 条件分岐の各ガードで、どの条件が false かを出す
- 「処理が呼ばれていない」ことが分かるよう、入口にもログを置く
- 両方の台のログを突き合わせて読む

調査用のログには `@memo: 調査用` と明記し、原因究明後に削除する。

## 10. 現在地と次の一手

### 動いているもの

- タイトル、キャラセレクト、ルール選択の同期
- 席の割り当てと権威の受け渡し
- キャラの座標と向きの同期 (ホスト → ゲスト方向を確認済み)
- バブルの生成・配置・王冠の同期
- 試合フェーズ、勝ち点、ラウンド終了の同期

### 次にやること

1. **非権威側のコライダーを残す** (3 章)。
   ゲスト側でキャラが落下し続ける問題の直接の原因
2. **キャラセレクトの空き枠を CPU にする** (5 章)
3. **切断・クラッシュ対策** (6 章)
4. 調査用ログの削除
5. リザルト画面の同期
